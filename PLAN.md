## Зачем

Два Windows-компьютера. Приложение показывает проекты и синхронизирует контекст. Нужны автосинхронизация всех проектов и автозапуск. Окно потом сужается. Git-схема контекста остаётся прежней, чтобы старый клиент на второй машине продолжал работать.

## Что уже умеет синхронизация

`ProjectManagerState` (`lib/state/project_manager_state.dart`):

- При выборе проекта и на старте, если выбран первый проект, вызывается `_armContextSyncForSelectedProject`.
- Следит за `.ai` выбранного проекта, debounce 20 с.
- Интервал из настроек (`ContextSyncSettings.syncInterval`, по умолчанию 5 минут, диапазон 1–120) крутит только выбранный проект.
- Кулдаун 5 минут на `contextId`. Для причин `project-selected` и `ai-watch` — один автозапуск на проект за сессию (`_autoCursorSyncDone`). Интервал и ручная кнопка этим ограничением не режутся.
- Пока идёт sync или Cursor CLI, новый запуск пропускается, очереди нет.
- Смена выбранного проекта увеличивает `_syncRunGeneration` и обрывает текущий sync.

Этого мало: закрытое приложение молчит, невыбранные проекты не синкаются, после входа в Windows процесс сам не стартует.

## Фаза 1. Автосинхронизация всех проектов

Статус: сделано.

Цель: при включённом sync на старте и по интервалу проходят все проекты из `projects.json`, по одному. Протокол git и папки UUID не меняются.

Сделать в `ProjectManagerState`:

- Очередь `_runContextSyncAll({required String reason})`. Снимок списка проектов на старт очереди. Следующий проект начинается после завершения предыдущего. Повторный вызов, пока очередь идёт, не стартует вторую.
- `initialize()` после загрузки проектов ставит очередь с reason `startup`, даже если список пуст (тогда очередь ничего не делает). Выбор первого проекта и его watch оставить.
- `_restartContextSyncInterval` вызывает очередь всех проектов, а не только выбранный.
- Для `startup` и `interval` признак «продолжать» не привязан к id выбранного проекта. Смена проекта по-прежнему обрывает sync, который вооружил сам выбор (`project-selected`, `ai-watch`).
- Кулдаун 5 минут и git-lock сохранить. Если pull не удался из‑за сети, не крутить tight loop: подождать 15 с, затем 30 с, затем 60 с, дальше до следующего тика интервала. Три попытки на один проход очереди.
- Ручная кнопка «Синхронизировать сейчас» по-прежнему синкает выбранный проект.

Проверка: тест на очередь из двух проектов (второй стартует после первого, параллельного `syncProject` нет) и на то, что reason `interval` не попадает под `_autoCursorSyncDone`. Ручной прогон не обязателен, если тест закрывает очередь.

## Фаза 2. Один процесс и автозапуск

Статус: сделано.

Цель: после входа в Windows запускается один экземпляр, окно свёрнуто, сразу выполняется стартовая очередь из фазы 1.

- Mutex в `windows/runner/main.cpp` до создания окна. Имя `Local\ProjectManager`. Если mutex уже есть — найти окно с заголовком `Project Manager`, показать и выйти.
- Аргумент `--minimized`: окно создаётся свёрнутым. Планировщик передаёт этот аргумент.
- Настройка в существующем диалоге настроек: «Запускать при входе в Windows». Вкл — `schtasks /Create /F /TN "ProjectManager" /SC ONLOGON /DELAY 0000:30 /RL LIMITED` на собранный `project_manager.exe` с `--minimized`. Выкл — `schtasks /Delete /F /TN "ProjectManager"`. Путь к exe хранить в настройках; по умолчанию exe рядом с текущим процессом.
- Ключ HKCU Run не использовать: у планировщика есть задержка, сеть к этому моменту чаще уже есть.
- Закрытие окна завершает процесс, как сейчас. Автозапуск поднимает его снова на следующем входе. Отдельный трей не делать.

Проверка: второй запуск exe активирует первое окно. Задача планировщика появляется и удаляется вместе с тумблером. В тесте планировщик не вызывать: проверить сборку команды и разбор `--minimized`.

## Фаза 3. Папка settings

Статус: сделано.

Папка в корне клона называется `settings`. Это не UUID и не `backups`: старый клиент и так не путает её с проектом, а имя `backups` похоже на свалку bak и логов, которую в репозиторий класть не нужно.

Старый клиент копирует в `.ai` только каталог с именем, равным `contextId`. `contextId` всегда UUID, поэтому `settings/` в проект не попадает. `git pull` привозит её как обычный каталог, `git add -A` её не удаляет.

Содержимое:

- `settings/cursor/skills/` ← `%USERPROFILE%\.cursor\skills`
- `settings/cursor/rules/` ← `%USERPROFILE%\.cursor\rules`
- `settings/cursor/memories.json` ← `%USERPROFILE%\.cursor\memories.json`
- `settings/cursor/mcp.json` ← `%USERPROFILE%\.cursor\mcp.json` целиком, токены на месте

Не делать шаблон и не заменять секреты на `${ENV}`. `settings.json` редактора в эту папку не класть: там абсолютные пути JDK, FVM и Maven этой машины. Бинарь grafana, Happ, lan3 и транскрипты тоже не копировать.

Тот же клон, тот же pull, тот же additive merge, тот же git-lock, после очереди проектов. Если в проходе менялся проект, сообщение коммита остаётся `sync: <uuid>`: `git add -A` захватит и `settings`. Если изменилась только `settings` — сообщение `sync: settings`.

Проверка: токен из фикстуры `mcp.json` без изменений лежит в `settings/cursor/mcp.json`. Папки UUID в тесте не меняются.
